## Bounded 0.58.2 footer reveal correction

The footer reveal path uses the outer ScrollArea's actual viewport, rather than deciding full visibility from its expanded paint clip. The actual viewport is reconstructed from the initial content origin and the viewport supplied to the ScrollArea closure. After the nested Explorer completes, the footer uses the current content minimum for its target coordinates. These two origins have different roles and must not be substituted for one another.

Only an existing footer reveal request can issue the correction. The requested vertical displacement `d` is the minimal movement needed to fit the requesting footer control in the actual viewport. Oversized controls, degenerate or nonfinite geometry, and zero displacement produce no correction target and preserve the existing reveal request. An immediate top-aligned target uses the current pre-footer content minimum, the viewport offset, the outer item spacing and `d`. This preserves egui's target coordinate and spacing conventions even if the nested Explorer changed the current content minimum. Any later footer or help scroll request retains normal last-writer priority for that target. The correction does not consume a global scroll delta, install a neutralizer, write ScrollArea state directly, change the exact visibility assertion, add a tolerance, or pad the tools/footer height.

The retained matrix, raw inputs, focus transitions and settling frames remain unchanged. The change is limited to footer reveal requests; the existing Explorer row/header handling and normal wheel, touchpad and scrollbar behavior remain separate. Source inspection can justify the candidate geometry but cannot establish that it passes: the exact original regression and fresh dual-platform CI remain required.

## Unchanged Automatic height contract

The existing 0.56.1 height behavior remains: a genuine primary-button vertical drag on the native top divider establishes a runtime preference. That choice survives report loading/clearing, tool switches, hide/show, disconnect and reconnect. Window constraints can limit the displayed allocation without overwriting the preference; regrowth restores it when space permits. Passive hover/click, horizontal movement and another control's drag do not establish a preference. The 245-point default and 150–500 range are unchanged, and neither a hard content cap nor guaranteed editor space is promised.

The new **Automatic height** action explicitly clears the runtime preference after the current panel pass and requests repaint. Subsequent layout uses the existing automatic content-sizing path; resetting does not substitute a fixed height, persist a setting or require restarting the app. A later genuine divider drag can establish an explicit preference again. The control is disabled when the panel is already automatic.

Reset takes precedence over divider capture for the current input frame and every layout pass in that frame. If Primary is still down, reset retains a wait-for-release guard. An existing wait is preserved even across focus loss. The original raw-input hook observes an actual Primary release to clear that wait for future frames; a release/repress batch stays blocked for its current frame. PointerGone or focus loss does not invent a release. A subsequent genuine Primary press/release sequence can recover the guard without synthesizing a release, and a later independently owned divider-drag frame may capture a new height. This prevents a stale held drag or another layout pass from immediately undoing reset while preserving a fresh real drag.

It measures both small buttons using their actual font/style, conditional horizontal frame padding and item spacing; the inside border does not add layout width. Only when the remaining row cannot fit the group does it end that row before creating the unchanged right-to-left group. Right alignment, native control order and normal button sizing remain intact. This addresses a source-review risk, not an observed runtime failure, and does not redesign other layouts. Production-frame coverage includes the 780×540 viewport at 13- and 18-point fonts plus normal width; the corresponding 0.58.0 resize checks passed on both CI platforms, within the failed aggregate run.
