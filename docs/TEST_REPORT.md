## Candidate sizing contract

Before any qualifying drag, the optional height is absent and the existing content-derived automatic shrinking remains in effect, including the short-content sidebar recovery behavior. A divider hover, a press without vertical movement, an unrelated drag or a secondary-button drag does not create a height preference.

A real primary-button vertical divider drag records the native allocation before content can enlarge it. Once set, that explicit height is retained through empty Tests, loading, loaded results, Clear report, hiding/reopening tools, switching tools and workspace reconnects. Later divider drags can enlarge or reduce it. The preference belongs only to the current frontend process; app restart returns to automatic sizing and does not restore a saved layout setting.

Ordinary window contraction may constrain the displayed panel, but must not overwrite the user's explicit height. Window growth restores that preference when space permits. The existing default request of 245 logical points, 150–500 range, panel identity, margins, control IDs and panel ordering remain in place. This change does not establish a hard content-height cap or guarantee room for the editor: tall non-scrolling content and very small windows retain their existing layout limits. Ctrl/Cmd+J remains the way to hide tools and return to the editor; Ctrl/Cmd+Shift+E retains its sidebar-access behavior.

The change does not alter report parsing, explicit Load/Refresh semantics, navigation/focus ownership, editor/history behavior, workspace operations, Java observation deadlines or refresh/retry policy. No dependency, remote-capability or package-inventory change is intended. See [the report guide](TEST_RESULTS.md) for report data boundaries.
